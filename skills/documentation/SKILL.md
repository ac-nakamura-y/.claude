# Documentation記述ルール

## 基本方針

- ファイル名は英語のkebab-caseで命名する
- 見出しに数字はつけない
- 区切り線は使わない
- 太字の使用は必要最低限にする

## コードブロック

- シェルコマンドのコードブロックはbashではなくshellを使う

```shell
mkdir -p docs/api-guides
cp template.md docs/api-guides/getting-started.md
```

## 表の書き方

- 表を使う場合、ヘッダーの区切り線は各列ともハイフン3つにする

| 項目 | 内容 |
| --- | --- |
| ファイル名 | 英語のkebab-case |
| コードブロック | `shell` を利用 |

## 要件定義書をアジャイルベースで作る設計

要件定義書を作成する依頼では、最初に全体要件を固定しすぎず、段階的に詳細化する。

- 目的と成果指標を先に定義する
- ユーザーストーリーを中心に要件を整理する
- 優先順位はMoSCoW（Must/Should/Could/Won't）で管理する
- リリース計画は複数イテレーション前提で記述する
- 受け入れ条件はストーリー単位で定義する
- 未確定事項はオープン課題として明示する

## 要件定義書の出力構成

要件定義書が必要な場合は、次の見出し構成を基本テンプレートとして使う。

| セクション | 記載内容 |
| --- | --- |
| 背景と目的 | 解決したい課題、ビジネスゴール、スコープ |
| 成果指標 | KPI、計測方法、達成基準 |
| ユーザーと課題 | ペルソナ、ジョブ、現状課題 |
| ユーザーストーリー | As a / I want / So that 形式の要件 |
| 優先順位 | MoSCoW分類と優先理由 |
| イテレーション計画 | スプリント単位の実装・検証計画 |
| 受け入れ条件 | ストーリーごとの完了条件 |
| 非機能要件 | 性能、セキュリティ、運用、監査 |
| リスクとオープン課題 | 未確定事項、依存関係、意思決定期限 |

## 進め方

- 初稿では全ストーリーを粗く定義する
- レビューごとに優先順位と受け入れ条件を更新する
- スプリント開始前に対象ストーリーのみ詳細化する
- スプリント完了時に学習内容を要件定義書へ反映する
