# Elixir Meeting Notes

資生堂エリクシール PoC の1週間は、月曜のクライアント定例、その直後のラップアップ、水曜の AC内部定例、木曜の BP内部定例で回る。このスキルは各会議を Notion の議事録 DB に1会議1ページで記録し、前の会議のページを次の会議の材料にする。フォルダや ID、メンバー、誤変換辞書などの固定値は `references/settings.md` にあるので、最初に読む。

実行者への確認は挟まない。材料を集めてページを作り、最後に URL と自分で判断したことを報告する。実行者は出来上がったページを Notion で直接直すので、途中で止めて聞くより、作り切ったページを早く渡すほうが役に立つ。

## Modes

モードは3つあり、依頼の言葉から決める。ラップアップのページは、ラップアップでの議論の土台として、クライアント定例の結果を記録したものである。

| モード | 対象の会議 | 会議前 | 会議後 |
| :-- | :-- | :-- | :-- |
| wrap | ラップアップ | クライアント定例の決定事項・TODO・次回アジェンダを記録する | なし |
| ac | AC内部定例 | アジェンダを作る | 決定事項と TODO を追記する |
| bp | BP内部定例 | アジェンダを作る | 決定事項・TODO・次回クライアント定例アジェンダを追記する |

ac と bp が会議前か会議後かは、その会議の議事メモがあるかで決める。Drive に Gemini 議事メモがあるか、実行者が文字起こしを貼るかリンクを渡していれば会議後、どちらもなければ会議前である。依頼に日付がないとき、会議前は今日以降で直近のその曜日、会議後は今日以前で直近のその曜日を対象にする。wrap の日付は、使うクライアント定例の議事メモの実施日にする。定例の曜日や時刻は変わることがあるため。

## Workflow

作業は次の順に進める。Notion の読み書きはすべて `scripts/notion_minutes.py` で行う。

1. `references/settings.md` を読む。
2. 対象の会議名と日付で `find --on` を実行し、既存のページを探す。ページがなければ新しく作る。ページがあれば `read` で本文を見て、本文が空なら人が器だけ先に作ったものとしてそこへ追記する。会議前と wrap で本文がすでにあれば、人が書いたものなので手を付けず、その URL を報告して終える。会議後は本文があってもそこへ追記する。
3. Materials の節に沿って材料を読む。
4. Writing の節の形式でページの本文を Markdown に書き、一時ファイルに保存する。
5. 新しく作るなら `create`、既存のページへ足すなら `append` で書き込む。書き込んだら `read` でページを読み返し、節と入れ子の構造が崩れていないか確かめる。
6. Report の節に沿って報告する。

必須の材料が見つからないときは、代わりの材料で埋めずに、その時点で止めて見つからなかったものを報告する。wrap ではクライアント定例の議事メモ、会議後の ac と bp ではその会議の議事メモが必須である。

## Materials

### Wrap

wrap の材料は、クライアント定例の議事メモと定例資料の2つである。議事メモは、実行者が Slack のリンクを渡したら、そのスレッドに添付された HTML を読む。渡されていなければ、Slack チャンネル `C0AJSBBGTFW` の最近のメッセージとスレッドを読み、 `YYYYMMDD_shiseido_poc_teireikai-minutes_vN.html` が添付された最も新しいものを使う。投稿の本文は「議事メモ送ります」程度で、メッセージ検索ではファイル名に当たらないため、検索ではなくチャンネルを読む。HTML は大きいので、タグを外したテキストに変えてから読む。

決定事項は、後半の「文字起こし詳細」で発言を確かめてから書き、そのタイムスタンプを出典にする。前半の要約は確認用に読むが、要約だけを根拠にしない。前半の「論点・リスク（示唆）」は議事メモを書いた人の見立てなので、決定事項にも TODO にも入れない。

定例資料は、Drive の定例資料フォルダで同じ日の `_YYMMDD` を読む。スライドのページ番号と、次回定例以降のスケジュールを拾う。

### AC and BP before the meeting

会議前のアジェンダは、前の会議のページと当週の資料から組み立てる。Notion のページは `find <会議名> --before <対象日>` で探し、 `read` で読む。

| 材料 | 取り方 | 拾うもの |
| :-- | :-- | :-- |
| 直近のラップアップ | Notion `[資生堂] maruttoラップアップ` | 決定事項、TODO、次回クライアント定例アジェンダ |
| 前回の AC内部定例 | Notion `[資生堂] AC内部定例` | TODO と決定事項 |
| 前回の BP内部定例 | Notion `[資生堂] marutto内部定例` | TODO と決定事項 |
| 当週の定例資料 | Drive 定例資料フォルダの `_YYMMDD` | 全体スケジュール、最終報告や第2回PoC の状態 |
| 当週の制作定期MTG | Drive 議事録フォルダで `制作定期MTG` を含み、対象日の直前の月・火のもの | 制作の進み具合と確認事項 |

bp では、上の材料に当週の AC内部定例のページを加え、そこで決まった AC の結論を BP に持っていく着地案にする。前の会議のページに決定事項がまだ書かれていなければ、その会議の Gemini 議事メモから拾う。

BP内部定例には井上さんと渡部さんが出るので、載せる議題を選ぶ。AC 社内の体制、コスト負担、他社の見積もりの話は載せない。AC内部定例で結論が出ていない議題も、BP に出す前に AC の結論が要るため載せない。ただし AC内部定例で「BP にも共有する」と決めたものは載せる。

### AC and BP after the meeting

会議後の材料は、その会議の Gemini 議事メモ（ `_議事メモ_1` と `_議事メモ_2` があれば両方）か、実行者が渡した文字起こしである。ファイル名は `references/settings.md` の Meetings の表にある。

### Checks on every source

Drive の議事メモは、ファイル名の日付と本文冒頭の日付が一致するか確かめる。違っていれば材料に使わず、報告に書く。実際に `20260921_資生堂エリクシール制作定期MTG_議事メモ` の中身は、6/15 の別の会議だった。制作定期MTG にはエリクシール以外の話（営業活動、他社案件、人事や契約）が混ざるので、エリクシール案件に関係する話だけを拾う。

## Writing

### Record format

wrap のページと、ac・bp の会議後に追記する部分は、決定事項・TODO・次回クライアント定例アジェンダの3節で書く。ac の会議後は、次回クライアント定例アジェンダの節を省く。要約、議論の概要、参加者や材料の一覧は書かない。参加者は Notion のプロパティに入れ、材料は報告に書く。

各節の粒度を次に示す。

- 決定事項：会議で合意したことと、方針が決まったことだけを書く。話題ごとに見出し3でまとめる（例：最終報告、第2回PoCの進行について、その他）。1項目は短い見出しのような1行にする。経緯や相手の発言が要る項目は、子の箇条書き1つに2〜3文で書き、末尾に `（定例 MM:SS）` の形で出典を付ける。説明の要らない項目は1行で書き、末尾に出典を付ける。
- TODO：次の会議までに進める作業と、先方からの返事待ちを、成果物の単位で1行ずつ書く。具体的な修正点は子の TODO にする。担当、期限、出典は書かない。その日のうちに済む連絡（資料の送付、日程調整、リスケの連絡）は書かない。返事待ちは「穐吉様から〜をいただく」のように書く。
- 次回クライアント定例アジェンダ：定例資料のスケジュールと今日の決定から、次回の定例で扱う議題を組み立てる。発言で次回の議題と明言されていなくてよい。議題を番号付きで書き、その下に論点を子の番号付きで書く。

資料の箇所はスライドのページ番号（P7、P23）で書く。スライドの中の通し番号（追加スライド②など）は、読み手がどのページか分からないので使わない。

11/9 のクライアント定例をもとに、実行者が直した完成形を次に示す。粒度と書き方の基準にし、内容は流用しない。

```markdown
## 決定事項
### 最終報告
- P7「達成」の表現
  - 穐吉様は、「達成」と書くと①②はもう済んだように見えると指摘した。原嶋さんは「全工程を PDCA で磨き続ける」と説明し、「さらに強化」とは書かずに口頭で補うことで落ち着いた。トーンは「課題は制作だけ」ではなく「主な課題は制作」にする（定例 10:00〜13:42）。分かりにくさが残るため、原嶋さんが見せ方を見直す（定例 13:48）
- P23の追加スライド（取り組みから承認事項へ）
  - いま載っている事例は一般的なルールに見える、と穐吉様から指摘があった。「エリクシールではこう言わない」といった、ブランドらしさに関する指摘事例を入れれば、ルールブック化でやりとりが減ることが伝わる。中村さんが追加すると回答した（定例 18:06〜19:02）
- 資料全体のトーン
  - 穐吉様の部署では、資料を「上の2行だけで伝わる」水準で作っている。正確さより分かりやすさを優先してほしいとの要望で、原嶋さんは可能な限り対応すると答えた（定例 21:07〜22:42）
### 第2回PoCの進行について
- プランで主役商品を1〜2点に絞っても、ほかの商品は外さず、クリエイティブでは強弱をつけて見せる形とする（定例 32:13〜32:42）
- 第2回PoC のスケジュールとプランの方針は、大筋で了承された。細かい点は進めながら調整する（定例 31:42・33:34）
- 11/13 以降も、毎週月曜14時の定例を続ける（定例 36:48〜37:14）
### その他
- 島影様への概要説明は定例の場では行わず、個別に実施する（定例 36:14〜36:34）
## TODO
- [ ] 最終報告資料について、穐吉さまからFBをいただく。
- [ ] 最終報告資料のアップデート
  - [ ] P7「達成」の表現
  - [ ] P23の追加スライド（取り組みから承認事項へ）
- [ ] 第2回PoCの制作進行
## 次回クライアント定例アジェンダ
1. 最終報告後に受け取ったフィードバック内容の振り返り
  1. それを受けたネクスト事項の議論
1. 2回目PoCについて
  1. 2サイクル目・2ラリー目の実施条件と判断タイミング
  1. 1月下旬に最終判断の仕切りで良いかの確認
```

### Agenda format

ac と bp の会議前のページは、次の形で書く。会議後に Record format の3節を末尾へ追記するので、会議前のページには決定事項と TODO の見出しを置かない。

```markdown
## 本日のゴール
- <この会議で決まれば終了となること>
## アジェンダ
1. 現在進捗の確認
1. 次回クライアント定例アジェンダの確認
1. <議題>
## 現在進捗（M/D時点）
### <作業のまとまり（最終報告、第2回PoCの制作など）>
- [x] <終わったこと>（<根拠>）
- [ ] <進めていること>
## 次回クライアント定例アジェンダ（案）
1. <議題>
  1. <論点>
## 議題
### <議題名>
- 背景：<1〜2文>（<出典>）
- 今日確認したいこと：<問い>
```

現在進捗は、前回のページの TODO を作業のまとまりごとに並べ直したものである。完了の根拠（議事メモの発言、資料の記載、Notion でチェック済み）があるものだけ `[x]` にし、根拠を括弧で添える。根拠がないものは `[ ]` のまま残す。bp の本日のゴールは、論点ごとに「<論点>：AC としては<結論>で合意したい」と書き、AC の結論が当週の AC内部定例にないときは論点だけを書く。

### Common rules

材料にない数値、日付、発言、決定は書かない。人名と社名は `references/settings.md` の誤変換辞書で直し、辞書にない崩れた名前は推測で埋めずに「不明」と書く。社内向けの文書なので常体で書き、敬称は資生堂様の方に「様」、AC と BP の人に「さん」を付ける。

## Notion

スクリプトはスキルのディレクトリで実行する。トークンは `~/.config/notion/token` から読む。

```bash
python3 scripts/notion_minutes.py find "[資生堂] maruttoラップアップ" --on 2026-11-09
python3 scripts/notion_minutes.py find "[資生堂] AC内部定例" --before 2026-11-11
python3 scripts/notion_minutes.py read <page_url>
python3 scripts/notion_minutes.py create "[資生堂] maruttoラップアップ" 2026-11-09 body.md --people 原嶋,正者,中村,榎本 --source <議事メモの URL>
python3 scripts/notion_minutes.py append <page_url> after.md --people 原嶋,正者,中村,榎本
```

`create` は会議名、カテゴリ（資生堂様PJ）、日時、参加者、出典 URL（文字起こし/議論メモ）を入れてページを作る。 `append` はページの末尾に本文を足し、 `--people` を渡せば参加者も入れる。 `--dry-run` を付けると Notion に書かずに変換結果だけを出す。

参加者は、議事メモで出席が分かる AC のメンバーを入れる。会議前は出席が分からないので空にし、会議後の `append` で入れる。出典 URL は、wrap では Slack のスレッドの URL、それ以外では使った Gemini 議事メモの URL にする。

## Report

最後に、次の内容をチャットで短く報告する。

- 作ったか追記したページの URL と、モードと日付
- 使った材料と、日付の不一致などで使わなかった材料
- 確認せずに自分で決めたこと（日付の選び方、会議前か会議後かの判断、辞書にない名前の扱いなど）
