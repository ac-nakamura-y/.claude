# Do³

平日の朝、Do³ の日次セッション（ `do_daily_v2` ）で本人が送る返信を用意して送る。Do³ は営業日の朝、#01_1on1_prd_mktops などのチャンネルにメンバーごとのスレッドを立て、昨日終わらせたこと、今日の予定、判断に迷った場面、その判断基準を 1 問ずつ聞き、最後にまとめを示す。予実を共有し、どんな場面でどんな基準で判断しているかを積み重ねて見えるようにするのが Do³ の目的である。

このタスクは、まず tech のカレンダーで本人の監視の当番日かを確かめ、当番日なら監視の予定を入れて、10 時と 17 時に監視のセッションを始める。続けて前営業日に届いた依頼をトリアージし、本人が選んだものを Linear の Issue にする。その後、各問いへの返信を本人の言葉で書き、[Posting](#posting) のとおり下書きを置いて Ego Lite から送る。本人の確認を待つのは、トリアージ、今日の予定、判断に迷った場面の 3 つだけで、ほかの返信は文面ができたらそのまま送る。今日の予定は候補のうち空き時間に収まる分だけを選び、送ったら作業時間をカレンダーに入れ、挙げた作業ごとに Claude Code の背景セッションを始める。報告はすべて日本語で書く。

## Steps

毎回、次の手順を上から順に行う。手順を飛ばしたり、入れ替えたり、表にない手順を足したりしない。各手順の中身は「節」の列の節に従う。

| # | 手順 | 節 | 本人の確認 |
| --: | :-- | :-- | :-- |
| 1 | 監視：当番日なら監視の予定を入れ、監視のセッションを予約する | [Monitoring](#monitoring) | なし |
| 2 | スレッドを特定して読む | [Thread](#thread) | なし |
| 3 | トリアージ：前営業日の依頼から Issue の案を示し、選ばれた案を Issue にする | [Requests](#requests) | 案を選んでもらう |
| 4 | 昨日実施した業務を書いて送る | [Yesterday](#yesterday)・[Posting](#posting) | なし |
| 5 | 本日実施する業務：候補、文面、作業時間の表、セッションの表を示し、承認を得たら、送る、カレンダーに入れる、セッションを始めるの順に行う | [Today](#today)・[Calendar](#calendar)・[Kickoff](#kickoff)・[Posting](#posting) | 承認を得る |
| 6 | 判断に迷った場面の候補を 5 つ示し、選ばれたものを送る | [Judgment](#judgment)・[Posting](#posting) | 選んでもらう |
| 7 | 判断基準を書いて送る | [Judgment](#judgment)・[Posting](#posting) | なし |
| 8 | まとめの確認に返信する | [Summary](#summary)・[Posting](#posting) | なし |
| 9 | [Monitoring Report](#monitoring-report) の表、送った返信と止まって本人に任せた返信、作った Issue、[Events](#events) の表、[Kickoff Report](#kickoff-report) の表、失敗したこととそのエラーをまとめて報告する | | なし |

手順は 1 つずつ行う。前の手順を終えるまで（返信を送る手順では、届いたことを確かめるまで）、次の手順の材料集め、サブエージェントの起動、文面づくりを始めない。1 通のメッセージに 2 つの手順の文面や確認を入れない。本人の確認がある手順では、示したところで手番を終え、本人の返事を待つ。手順 1 で予約した監視の開始時刻が届いたときだけは、どの手順の途中でも [Monitoring Session](#monitoring-session) のとおりセッションを始める。

スレッドで本人がすでに答えた問いは、その送信を済んだものとする。今日の予定を本人がすでに送っていても、手順 5 のカレンダーとセッションは行う。どちらも、すでにある予定とセッションを作り直さない。

送ったあとは毎回スレッドを読む。Do³ が深掘りの問いを挟んでいれば、次の手順に進む前に答えて送る。たとえば「どんな形のアウトプットになっていて誰が見れば確認できる状態までできましたか？」には、一覧にせず「いずれもスライドもしくは artifact で、チームメンバーが見て確認できる状態まで進めました。」のように 1〜2 文で答える。

## Monitoring

tech のカレンダーで今日が本人の監視の当番日かを確かめ、当番日なら監視の時間を本人のカレンダーに入れ、監視のセッションを始める時刻をこの会話の中に予約する。監視の時間は次の 2 つである。

| 予定 | 時間 | セッションの開始 |
| :-- | :-- | :-- |
| [監視] 午前監視 | 10:00〜11:00 | 10:00 |
| [監視] 午後監視 | 17:00〜17:30 | 17:00 |

### Duty

Google Calendar の `list_events` を次の引数で呼ぶ。tech のカレンダーは本人の主カレンダーとは別なので、 `calendarId` を渡す。

```json
{"calendarId": "c_oaoql0aoncppe1elsqjgma8r20@group.calendar.google.com", "startTime": "<今日>T00:00:00", "endTime": "<今日>T23:59:59", "fullText": "平日監視"}
```

`start.date` を持つ終日予定のうち、summary がちょうど `平日監視：中村` で、 `status` が `cancelled` でないものがあれば当番日とする。なければ、この手順を終えて手順 2 に進む。

### Monitoring Events

当番日なら、今日の主カレンダーを `list_events` で読み、上の表の予定ごとに、summary が同じ予定が今日すでにあるかを確かめる。なければ `create_event` で作る。招待する人は付けず、 `calendarId` と `timeZone` は渡さない。

| field | value |
| :-- | :-- |
| summary | 表の予定 |
| startTime・endTime | 表の時間（UTC オフセットを付けない ISO 8601） |
| colorId | `2` （[Colors](#colors) のその他） |

作った予定は、[Slots](#slots) で埋まっている時間に数える。

### Booking

当番日なら、今の時刻（JST）と表の予定ごとに比べ、次のとおり扱う。

| 状況 | 行うこと |
| :-- | :-- |
| セッションの開始より前 | ToolSearch を `{"query": "select:CronCreate", "max_results": 1}` で呼んで読み込み、CronCreate を下の引数で呼ぶ |
| セッションの開始を過ぎ、予定の終わりより前 | 予約せず、すぐに [Monitoring Session](#monitoring-session) のとおりセッションを始める |
| 予定の終わりを過ぎている | 予約もセッションもしない |

```json
{"cron": "0 <開始の時> <今日の日> <今日の月> *", "recurring": false, "prompt": "<予定> の開始時刻になった。手順書 do3 の Monitoring Session のとおり監視のセッションを始め、ほかの手順は進めない。"}
```

予約はこの会話の中だけにあり、会話が本人の返事を待っている間や手順 9 を終えたあとも、開始時刻が来ると届く。届いたら [Monitoring Session](#monitoring-session) のとおりセッションを始め、その結果だけを報告する。本人の確認を待っている途中であれば、続けて待っている確認を示し直して手番を終える。

### Monitoring Session

セッションは Skill `session-kickoff` の Start に従って始める。

| 項目 | 値 |
| :-- | :-- |
| 名前 | `<予定> <今日の日付（YYYY-MM-DD）>` 。例： `[監視] 午前監視 2026-11-27` |
| フォルダ | このコンピューター（[Start](#start) と同じ置き場に scratch のフォルダを作り、 `-w` を付けない） |
| 指示のファイル | この実行の scratchpad に `監視を開始してください！` の 1 行だけを書く |
| 追加の引数 | `--model claude-opus-5-5 --effort xhigh` |
| 固定 | しない |

`claude agents --json --all` に同じ名前の `background` のセッションがあれば、始めない。CLI にログインしていなければ、始めずに「CLI へのログインが必要（ `claude auth login` ）」と報告する。

### Monitoring Report

手順 1 を終えたら、次の表を示す。予約した行の「結果」には CronCreate が返した実行の時刻を、始めた行には `<id>` を、何もしなかった行にはその理由（当番日ではない、予定の終わりを過ぎている、同じ名前のセッションがある、始められなかった）を書く。予約は Do³ の会話が開いている間だけ届く。

```markdown
| 予定 | カレンダー | セッション | 結果 |
| :-- | :-- | :-- | :-- |
| [監視] 午前監視 | 作った | 予約した | 10:00 |
| [監視] 午後監視 | すでにある | 予約した | 17:00 |
```

## Thread

スレッドの読み書きには、チャンネルの ID と親メッセージの ts が要る。 `slack_search_public_and_private` を `do_daily_v2` と `on:<今日の日付（JST）>` 、 `include_bots: true` 、 `response_format: detailed` で検索する。Do³ はメンバーごとに `<@本人の ID> <@Do3> do_daily_v2` の形で親メッセージを立てるため、本人へのメンションを含むものを選び、その `Channel` の ID と `Message_ts` を使う。 `concise` 形式の結果には ts が出ない。スレッドがなければ、[Monitoring Report](#monitoring-report) の表と「今日の Do³ のスレッドはない」とだけ報告して手順を終える。監視の予約は残り、開始時刻が来ると届く。

本人の Slack ID は、Slack ツールが示すログイン中のユーザー ID で分かる。Slack の表示名は「（11日 午後休）」のような添え書きで日によって変わるため、本人の投稿は名前ではなく `from:<@本人の ID>` で探す。

## Done

Issue が完了したかは、次のどちらかに当たるかで決める。PR がマージされた Issue は、Linear の状態が残っていても完了とみなす。Linear の状態は変えない。

1. 状態の種類（ `statusType` ）が `completed` か `canceled` である
2. `get_issue` の `attachments` に GitHub の PR（URL が `https://github.com/<owner>/<repo>/pull/<番号>` のもの）が 1 本以上あり、どれも開いておらず、1 本以上がマージされている。定期タスク Auto Review が作るレビューの Issue（title が `<リポジトリ名>#<PR の番号> をレビューする：` で始まるもの）は、PR がマージされずに閉じられていても完了とする

PR の状態は PR ごとに `gh pr view <PR の URL> --json state,mergedAt` で読む。 `state` が `OPEN` なら開いている、 `MERGED` ならマージ済み、 `CLOSED` ならマージされずに閉じられている。PR が 1 本もない Issue は 1 だけで決める。 `list_issues` の結果には `attachments` が出ないため、判定する Issue はすべて `get_issue` で読む。

この判定は、昨日終わらせたこと、今日の候補、依頼の照合、固定の解除で使う。

## Requests

前営業日に本人へ届いた依頼のうち、まだ Issue のないものを、本人が選んだ分だけ Linear の Issue にする。次の 1〜8 を毎回この順に、書いたツールと引数だけで行う。Backlog は対象にしない。Backlog の依頼は課題として担当と期限を持ち、Linear に写すと同じ作業が 2 か所に並ぶためである。

| # | 手順 | やること |
| --: | :-- | :-- |
| 1 | 範囲を決める | 前営業日の 0 時から今日の 0 時（JST）までとする。月曜は金曜の 0 時から今日の 0 時までとする |
| 2 | 議事録の一覧を取る | `~/batb/bin/batb query --recent --limit 50` を実行し、 `created` が範囲に入り、 `source` が Google ドキュメントのものを議事録とする。一覧は `updated` の新しい順に並ぶので、末尾の `updated` が範囲の始まりより新しければ、 `--limit` を 2 倍にして取り直す。 `batb query` 以外の方法では取らない。失敗したら、そのエラーを 7 で示し、議事録なしで 3 に進む |
| 3 | 議事録の本文を読む | 議事録 1 件ごとにサブエージェントを 1 つ起動し、 `source` の URL から Google Drive の `read_file_content` で本文を読ませる。[Selection](#selection) の「本人の作業と読めるもの」に当たる項目を、原文の引用、依頼者、作業の中身の 3 点で返させる。本人の名前は、Slack の検索結果で本人へのメンションに付く表示名から、添え書きを除いたものとして渡す。読めなかった議事録は 7 で示す |
| 4 | Slack のメンションを取る | `slack_search_public_and_private` で本人へのメンションを下の引数で検索し、 `cursor` を辿ってすべて取る。依頼かどうかにスレッドの文脈が要るときは、 `slack_read_thread` で親から読む |
| 5 | 依頼を選ぶ | 3 と 4 で集めた項目に [Selection](#selection) の 2 つの表を当て、案にする依頼を残す。同じ依頼が議事録と Slack の両方や複数の会議に出るときは、1 つにまとめる |
| 6 | 既存の Issue と照らし合わせる | [Matching](#matching) のとおり照らし合わせ、当たった依頼を案から除く |
| 7 | 案を示す | [Proposal](#proposal) の表と、案にしなかった依頼を示す |
| 8 | Issue を作る | 本人が選んだ案だけを、[Creation](#creation) のとおり作る |

```yaml
keywords: ["<@本人の ID>"]
after: "<前営業日の 0 時（JST）の Unix 時刻>"
before: "<今日の 0 時（JST）の Unix 時刻>"
natural_language_query: ""
sort: timestamp
response_format: detailed
include_context: false
```

### Selection

案にするのは、本人がこれから手を動かして仕上げる作業のうち、作るものと終わりがあり、その場では終わらないものに限る。

| 入口 | 本人の作業と読めるもの | 読めないもの |
| :-- | :-- | :-- |
| 議事録 | 本人が担当と書かれた宿題、文字起こしで本人が引き受けた作業 | 担当が書かれていない項目、決定事項の記録 |
| Slack | 本人への依頼・確認 | cc だけの投稿、お礼や相槌、bot の定型投稿、複数人宛で本人が引き受けていない依頼 |

本人の作業と読めても、次に当たるものは案にしない。

| 除くもの | 例 |
| :-- | :-- |
| 予定の操作 | 会議の設定、招待の送付、日程の調整 |
| その場で終わる作業 | スレッドで返せば済む回答、返事を求められていない共有への目通し、権限の付与、リンクの転送 |
| 済んでいる作業 | 本人が対応済みと返信した依頼、会議中に済ませた作業、期限が過ぎた当日中の作業 |
| PR のレビュー | 定期タスク Auto Review が PR ごとに Issue を作る |
| 終わりのない作業 | 会議への出席、毎回の役割 |
| 中身を読み取れない作業 | 何をするかが議事録に書かれていない宿題 |

### Matching

照合先は、[Today](#today) で取った Issue と、 `list_issues` を `assignee: me` と `createdAt: -P14D` で取った Issue を合わせ、[Done](#done) で完了とみなすものを除いたものである。後者で、Triage やバックログにある Issue も拾う。一覧の本文は途中で切れたり出なかったりするため、照合先はすべて `get_issue` で読む。 `list_issues` の `query` は本文の URL を拾わないため、照合には使わない。

照合は次の 2 つで、どちらかに当たれば案にしない。

| 照合 | 当たりとするもの |
| :-- | :-- |
| ファイル | 依頼の文面が指す Google のスライド・スプレッドシート・ドキュメントの ID が、Issue の本文にある |
| 作業 | 言い回しが違っても同じ作業を扱う Issue がある。着手中の資料作成の Issue があれば、同じ資料への手直しの依頼も当たりとする |

議事録の Google ドキュメントは出典なので、ファイルの照合には使わない。1 つの会議から別々の宿題が出るためである。

### Proposal

案は次の表にまとめる。title は `[クライアント] 何をするか` の形で一文で書き、project は [Creation](#creation) の手順で決めて、付けないときは「なし」と書く。出典にはリンク付きの出典名と依頼の要約を、補足には宛先や担当が読み取れないなど、本人が判断に要ることを書く。

```markdown
| # | title | project | 出典 | 補足 |
| --: | :-- | :-- | :-- | :-- |
| 1 | [FDE] 〇〇の資料を作る | [FDE] 制作プロセス改善 | [11/13 FDE デイリー](https://docs.google.com/document/d/<doc_id>/edit)：〇〇の資料作成の宿題 | 担当の書き方が曖昧 |
```

表の後に、案にしなかった依頼を、出典、理由（[Selection](#selection) の除くもの、または照合で当たった Issue の URL）とともにすべて挙げる。案が `1` 件もなくても、この一覧は省かない。

### Creation

本人が選んだ案を、返信で直された点を反映して `save_issue` で 1 件ずつ作る。作った Issue 以外の Issue は、重複の印を付けることも含めて変えない。

| field | value |
| :-- | :-- |
| team | `marutto-ops` |
| project | 下の手順で決めたもの。決まらなければ渡さない（No project） |
| assignee | `me` |
| state | `Triage` |
| priority | `3` |

project は次の手順で決める。推測で別のプロジェクトを当てない。

1. `list_projects({ initiative: "[FDE]", member: "me" })` で取り、 `lead` が本人で、状態の種類が `completed` でも `canceled` でもないものを候補にする
2. title の先頭の `[クライアント]` と、名前の先頭の `[...]` が同じ候補を選ぶ。1 つならそれに決め、2 つ以上なら名前と作業の中身から 1 つに決めて、案の補足にその理由を書く
3. 同じ候補がなければ project を付けない

description は出典の引用から始め、Issue から依頼の原文へ辿れるよう、リンクを引用の中に埋める。引用は議事録や投稿を読み直して取る。リンク先は、議事録なら `https://docs.google.com/document/d/<doc_id>/edit` 、Slack なら検索結果の permalink とする。引用だけで作業が伝わらないときは、引用の下に背景と完了の条件を数行で足す。

```markdown
> **<依頼者>** [2026-11-13 15:18](<依頼の permalink>)
>
> <依頼の原文>
```

作った Issue は、title、project、URL を案ごとに示す。

## Yesterday

「昨日」は前営業日を指し、月曜なら金曜を振り返る。次の材料をすべて読み、その日の作業を集める。Issue になっていない作業も拾う。

| 材料 | 取り方 | 拾うもの |
| :-- | :-- | :-- |
| Google Calendar | `list_events` でその日の予定 | 会議名から、その準備にした作業 |
| Slack | `slack_search_public_and_private` を `from:<@本人の ID> on:YYYY-MM-DD` で検索し、必要ならスレッドを読む | 送付、レビュー、依頼への対応 |
| Claude のセッション | `list_sessions` （ `include_archived: true` ）と `list_events` で、その日の本人の発言を読む | 作業の中身。時刻は UTC のため JST に直して絞る |
| Linear | `list_issues` を `assignee: me` と `completedAt` 、または `creator: me` で取る | 完了した Issue、起票した Issue |
| GitHub | `gh search prs --author @me --merged-at "<範囲>"` と `gh search prs --reviewed-by @me --merged-at "<範囲>"` 。範囲は `YYYY-MM-DDT00:00:00+09:00..<翌日>T00:00:00+09:00` と JST で書く。日付だけでは UTC の 1 日になる | マージした PR、レビューした PR のマージ。PR を添付した Issue は、Linear の状態によらずその日に完了したものとする |
| git | `~/.claude` などのリポジトリの `git log` | 追加した Skill |

## Today

## Calendar

今日の予定の項目ごとに作業時間と分類を決め、送ったらその時間を本人の Google Calendar に入れる。この節でカレンダーに書き込むのは、作業時間の予定の作成と、ランチの移動だけである。

### Slots

空き時間は、今日の 9:30〜18:30 のうち、予定で埋まっていない時間とする。予定は Google Calendar の `list_events` で今日の分を取り、本人が辞退した予定（ `attendees` のうち `self` が真のものの `responseStatus` が `declined` ）を除いて、すべて埋まっている時間に数える。「予定なし」と表示する [雑務]・[タスク管理]・ランチ・バッファや、このタスクが作った作業時間も含む。空きは、文面を用意している時刻を 15 分単位に切り上げた時刻から数える。

作業時間は、項目 1 件ごとと、「各種RV」に添えたレビューの Issue 1 件ごとに決め、「各種RV」の行そのものには置かない。長さは、レビューの項目（[Items](#items) と同じ判定）と「各種RV」に添えたレビューの Issue が 15 分、それ以外が 1 時間である。

各項目は優先度順に、最も早い空きから 15 分単位で埋める。空きが項目の長さに足りなければ、残りを次の空きに続けて置き、1 つの項目を複数の時間に分けてよい。

ランチ（summary が「ランチ」の予定）は、11:30〜14:30 の中で同じ長さのまま 15 分単位で動かしてよい。動かすと項目を分けずに置ける、または分ける数が減るときに動かす。

置いた時間を、分けた時間 1 つにつき 1 行の表で示す。ランチを動かすときは、その行も入れる。分類は [Colors](#colors) の基準で決める。

```markdown
| 作業時間 | 予定 | 分類 |
| :-- | :-- | :-- |
| 9:45〜10:45 | MRTTOPS-9429: [資生堂] 最終報告資料の後半（今後の進め方・28 年度への言及・第2回 PoC のスライド）を直して原嶋さんに渡す | プロジェクト推進系 |
| 10:45〜11:00 | MRTTOPS-9506: [資生堂] サイクル1 初稿 → GAさま：レビュー | その他 |
| 11:00〜11:30 | MRTTOPS-9512: [FDE] ダッシュボードの集計を直す | チームマネジメント系 |
| 11:30〜12:30 | ランチ（13:00〜14:00 から動かす） | |
| 12:30〜13:00 | MRTTOPS-9512: [FDE] ダッシュボードの集計を直す | チームマネジメント系 |
```

### Colors

予定の色は分類で決め、 `create_event` の `colorId` で指定する。

| 分類 | 色 | colorId | 当てはまる作業 |
| :-- | :-- | :-- | :-- |
| プロジェクト推進系 | フラミンゴ | `4` | クライアントの案件や FDE のプロジェクトを進める作業（資料・実装・制作） |
| チームマネジメント系 | ラベンダー | `1` | 定例の準備、1on1、メンバーの育成、チームの運用ルールやダッシュボード |
| その他 | セージ | `2` | レビュー、社内の雑務、自分の仕組みの改善 |

### Events

送った一覧の項目をカレンダーに入れる。作業時間、分類、ランチの移動は、承認されたもの（本人がそこで直したものを含む）を使う。

作る前に今日のカレンダーを読み直し、項目ごとに、同じ日に同じ予定がすでにあるかを確かめる。summary が同じ予定のほか、Issue の項目では summary が `<Issue の ID>:` で始まる予定を同じものとする。すでにある項目は、分けた時間のどれも作らない。

承認した時間が埋まっている分けた時間だけを、[Slots](#slots) のとおりその場で置き直す。残りは承認した時間のままとし、その時間は埋まっている時間に数える。

ランチを動かすときは、読み直した今日のランチの予定の `id` （繰り返しの予定でも今日の分の id）を `update_event` に渡し、 `startTime` と `endTime` だけを変える。繰り返しの予定そのものは変えない。

作業時間の予定は、分けた時間 1 つにつき 1 件、 `create_event` で作る。招待する人は付けず、 `calendarId` と `timeZone` は渡さない。どちらも省くと、本人の主カレンダーに本人のタイムゾーンで作られる。

| field | value |
| :-- | :-- |
| summary | 項目の名前（[Items](#items) と同じ。Issue の項目では `<Issue の ID>: <タイトル>` になる） |
| startTime・endTime | 作業時間（UTC オフセットを付けない ISO 8601） |
| colorId | 分類の colorId |
| visibility | `private` （非公開） |
| availability | `AVAILABILITY_FREE` （予定なし） |
| description | Issue の URL。Issue のない項目には付けない |

「各種RV」に添えたレビューの Issue の summary は、 `get_issue` で読んだ `<Issue の ID>: <タイトル>` とする。

作り終えたら、作った予定（作業時間・summary・分類）、動かしたランチ、作らなかった項目とその理由（同じ予定がある、空きがない、作れなかった）を表で示す。

## Kickoff

今日の予定を送ってカレンダーに入れたら、改めて確認せずに、送った一覧の項目ごとに背景セッション（ `claude --bg` ）を始める。セッションは Remote Control 付きで始めるので Claude Desktop のサイドバーに並び、本人はそこから開いて続きを指示する。Kickoff が書き込むのは、指示のファイル、背景セッション、その固定と解除だけで、カレンダーの予定は [Calendar](#calendar) が作る。

### Items

一覧の 1 行を 1 件とし、Slack に表示される行の文面から一覧の番号を除いたものを、その項目の名前とする。今日の予定の書式では、Issue の項目の名前は `<Issue の ID>: <タイトル>` になり、行のリンク先が Issue の URL である。

次の項目にはセッションを始めない。

| 除く項目 | 理由 |
| :-- | :-- |
| 「各種RV」と、タイトルに「レビュー」「RV」を含む項目 | レビューは本人が行い、PR のレビューのセッションは定期タスク Auto Review が始める |
| `claude agents --json --all` で、 `kind` が `background` で `name` が Issue の ID か項目の名前を含むセッションがある項目 | 同じ作業のセッションがすでにある |

始める項目ごとに、セッションを始めるフォルダを決める。Issue の項目は `get_issue` で説明・添付・プロジェクトを読み、そこに出てくるリポジトリや PR を手がかりに、 `~/Documents` の直下、 `~/batb` 、 `~/.claude` にある Git のリポジトリから選ぶ。それぞれのリポジトリ名は `git -C <フォルダ> remote get-url origin` で分かる。どのリポジトリにも当てはまらない作業（スライドや資料づくりなど）は「このコンピューター」で始める。

```markdown
| # | 作業 | フォルダ | セッション |
| --: | :-- | :-- | :-- |
| 1 | MRTTOPS-9429: [資生堂] 最終報告資料の後半（今後の進め方・28 年度への言及・第2回 PoC のスライド）を直して原嶋さんに渡す | このコンピューター | 始める |
| 2 | MRTTOPS-9506: [資生堂] サイクル1 初稿 → GAさま：レビュー | | 除く（レビュー） |
| 3 | 各種RV（ac-llm-platform#371 ほか） | | 除く（レビュー） |
```

### Start

セッションは Skill `session-kickoff` に従って、次の順に始める。

1. `session-kickoff` の Start の 1 のとおり CLI のログインを確かめる。ログインしていなければ、セッションを始めずに止め、「CLI へのログインが必要（ `claude auth login` ）」と報告する
2. `session-kickoff` の Unpin のとおり固定を見直す。このタスクの決めた形は、名前が Issue の ID で始まるセッションである。その Issue が [Done](#done) で完了とみなせれば固定を外す
3. [Items](#items) で除いた項目を除き、残りの項目ごとに、[Brief](#brief) のとおり指示のファイルをこの実行の scratchpad に書き、承認の表で示したフォルダで、項目の名前をセッションの名前として始める
4. 始められたこと（状態が `failed` でないこと）を確かめた Issue の項目ごとに、セッションを固定する。Issue のない項目は、固定を外す時期が決まらないので固定しない

モデルは Opus 5.5（ `claude-opus-5-5` ）、effort は `xhigh` にするため、追加の引数は `--model claude-opus-5-5 --effort xhigh` とする。別名の `opus` は Opus 5 で始まるため使わない。

「このコンピューター」は、Claude Desktop がフォルダを指定しないセッションに使う置き場である。 `~/Library/Application Support/Claude/scratch-workspaces/4e1795b5-fd40-46bf-b0ee-c2ab9e8f762b/e56be690-54d3-4900-8fac-2d99cf8625c5/` に `scratch-<YYYY-MM-DD>-<16 進 6 桁>` のフォルダを作り、 `-w` を付けずに始める。このセッションは、サイドバーで「Remote Control」の下に並ぶ。

### Brief

次をこのまま書き、 `<>` を埋める。スレッドの permalink は、検索結果の `Permalink` から `?` 以降を除いたものである。Issue のない項目は、Issue の行と手順の 3 を除き、手順の番号を詰める。

```markdown
<名前> に取り組む。このセッションは、利用者が Do³ のスレッドで今日の予定に挙げた作業として、定期タスク do3 が始めた。

- Do³ のスレッド：<スレッドの permalink>
- Issue：<Issue の URL>

## 手順

1. 上のリンク先と、そこから辿れる資料を読み、今日どこまで進めるかを決める。進め方や完了の条件が読み取れないときは、推測で進めずに利用者に聞く
2. 作業に関わる Skill を確かめ、それに従って進める
3. 決めたこととその理由、参照した資料、置いた仮定、利用者から聞いたことなど、作業の前提が分かったら、その都度 Issue のコメントに書く。確認は要らない。人の名前には `@` を付けず、メンションしない
4. 他の人をメンションして伝える前、Issue の説明や状態を変える前、Slack・GitHub・Notion・Google Drive など他の人が見る場所に書き込む前は、全文と書き込み先を利用者に示し、利用者がはっきり同意するまで書き込まない
5. 区切りがついたら、成果物の所在と残りの作業を利用者に報告する
```

### Kickoff Report

始め終えたら、[Items](#items) の表の「セッション」の列を結果に置き換えて示す。始めた項目には `<id>` を、始めなかった項目には理由（レビュー、既存のセッションがある、CLI へのログインが必要、始められなかった）を書き、既存のセッションがある項目にはその `<id>` も添える。始められなかった項目は、Skill `session-kickoff` が返したものを表の後に書く。固定できなかった項目にはそのエラーを、固定を外したセッションがあればその id と名前を、表の後に書く。作業を終えたセッションは、本人が `claude rm <id>` で消す。worktree で始めたセッションは worktree ごと消える。

## Judgment

場面は、本人がチームでの役割（FDE チームのリーダーなど）として、チームや会社のミッションに向けて下した判断から選ぶ。文言の直し方のような個別作業の迷いは、抽象度が低いため採らない。材料は前営業日の Claude のセッションでの本人の発言である。セッションが多いときはサブエージェントに読ませ、セッションごとに本人の判断を、発言の短い引用、決めたこと、その理由の 3 点で抜き出させる。

手順 6 では、候補を 5 つ、そのまま送れる文面で示し、本人に 1 つ選んでもらう。1 つに決め打ちしない。文面は、1 文目で迷った論点を抽象的に述べ、2 文目で具体的な場面を 1〜2 件挙げ、3 文目でミッションと懸念のどこで板挟みになったかを書く。本人が選んだ候補を、返信で直された点を反映して送る。

手順 7 の基準は、送った場面に合わせて書く。1 文目で基準を「」でくくって示し、続けてそれぞれの場面への当てはめを書き、最後に一般化した使い分けと、それをチームでどう使うかを書く。

## Summary

Do³ はここまでの内容をまとめて「このまとめ内容で合っていますか？」と聞く。返信は「ありがとうございます、相違ないです。」に、書きながら気づいたことを 1〜3 文で添える。気づきには、その日の判断が過去の判断や本人が重視する枠組み（QCD など）とどうつながるか、チームにどう広げるかを書く。「はい、合っています」だけの返信にはしない。Do³ は返信を待たずに、上長宛ての最終のまとめを投稿することがある。まとめの確認が届いたら、すぐに文面を用意して送る。

```text
ありがとうございます、相違ないです。
本日記載した判断は、一見するとどのような軸で判断したか自分の中で整理できていませんでしたが、書きながら自身の中で重視しているQCDのフレームワークに落とし込めることに気がつきました。
```

## Posting

返信はすべて、Slack の下書きを置いてから、Skill `ego-browser` に従って Ego Lite でその下書きを送信する。Do³ のチャンネルは社外と共有しているチャンネル（Slack Connect）のため、 `slack_send_message` は `mcp_externally_shared_channel_restricted` で失敗する。下書きを経るのは、Linear のリンクの Markdown（ `[MRTTOPS-xxxx: タイトル](URL)` ）を Slack のリンクに変えて送るためである。

1 通ごとに次の 1〜5 を行う。

| # | 手順 | やること |
| --: | :-- | :-- |
| 1 | 問いを確かめる | `slack_read_thread` でスレッドを読み、最後の Do³ の投稿がこれから答える問いで、本人がまだ答えていないことを確かめる。問いがまだ届いていなければ、文面を示して止まり、問いが届いたら知らせるよう本人に頼む |
| 2 | 下書きを置く | `slack_send_message_draft` に、[Thread](#thread) で決めたチャンネルの ID、親メッセージの ts（ `thread_ts` ）、文面を渡す。 `attached_draft_exists` で失敗したら、本人の書きかけかもしれないので消さずに止め、Slack で送るか消すよう本人に頼む |
| 3 | スレッドを開く | Ego Lite で `https://app.slack.com/client/T03RBH796SE/<チャンネルの ID>/thread/<チャンネルの ID>-<親メッセージの ts>` を開く。スレッドの入力欄（ `[data-qa="threads_flexpane"] [data-qa="message_input"]` ）の文字列に、文面の 1 行目の先頭 `10` 文字が入るまで、 `20` 秒を限りに待つ |
| 4 | 送信する | スレッドの送信ボタン（ `[data-qa="threads_flexpane"] button[data-qa="texty_send_button"]` ）をクリックする。Return キーは改行になるため使わない |
| 5 | 届いたか確かめる | `slack_read_thread` で読み直し、本人の返信として文面が届いたことを確かめる。確かめたら、Ego Lite のタスクスペースを `finish({ keep: [] })` で閉じる |

次のときは、送り直しや別の送り方をせずに止め、何が起きたかと、本人が Slack から送れるようにコードブロックの文面を示す。

| 起きたこと | 本人に頼むこと |
| :-- | :-- |
| Ego Lite がログイン画面（URL に `signin` を含む）に移った | `handOff()` してから、Ego Lite で Slack にログインする |
| 3 で入力欄に下書きが出ない | Slack の「下書きと送信済み」で下書きを確かめて送る |
| 4 のクリックが権限の確認で拒まれた | Slack のスレッドで下書きを送る |
| 5 で返信が届いていない | Slack のスレッドを確かめ、届いていなければ送る |

## Style

文面は、本人が手を入れずに送れる日本語で書く。本人の過去の返信を `in:<#チャンネル> from:<@本人の ID>` で読み、言い回しをそろえる。です・ます調にし、挨拶は最初の返信にだけ付ける。一覧の返信には、上の例と同じ 1 行の前置きを付ける。場面、基準、気づきの文章は Skill `humanizer` で見直し、強調のためだけの対比、言い直しの締めの一文、ダッシュを除く。
