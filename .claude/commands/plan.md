ユーザが渡した要件: `$ARGUMENTS`

あなたはプロジェクト設計者です。以下の手順で設計ドキュメントを生成してください。

## 手順

1. `docs/architecture.md` と `docs/quality.md` を読み、レイヤ構成 / 命名規約 / ハーネスを把握する。
2. 既存のコードベースを Glob / Grep で軽く確認し、どこまで作られているかを掴む。
3. ユーザが渡した要件を、**縦割りスライス** で実装可能な単位に分解する。
   - ❌ 「ドメインモデル全部 → Repository 全部 → UI 全部」
   - ✅ 「基盤 → 機能 A を DB〜UI まで縦に通す → 機能 B を縦に通す」
4. `docs/tasks/<YYYYMMDD>-<短い英語スラッグ>.md` を新規作成し、
   以下の節を Markdown で書く：

```markdown
# <機能名>

## 背景と目的
（なぜ作るか。1〜3 段落）

## スコープ
- 含むもの
- 含まないもの

## 縦割りスライスの順序
1. スライス #1: <ユーザが画面で触れる最小動作>
2. スライス #2: <次に触れるようになるもの>
3. …（4〜8 個まで）

## 各スライスの受け入れ条件
### スライス #1
- [ ] 画面で〇〇が××できる（動画で見せられる）
- [ ] 本物のインフラ（DB / API）に接続されている
- [ ] quality.md のハーネスがすべて green

## 非機能要件 / 制約
- パフォーマンス・セキュリティ・互換性など
```

## 守ること

- スライスは **サイクル 1 回で実装しきれる粒度** に揃える（大きすぎたら分割）。
- 受け入れ条件には、モックで回避できない「ユーザから見える挙動」を必ず入れる。
- 書き終えたら、生成したファイルのパスを stdout に 1 行で出力して終了。

このファイルは loop.sh の project-manager フェーズで
「次に着手するスライス」を選ぶ入口になります。
